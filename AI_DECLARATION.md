# AI Usage Declaration — Fair-Share

**Project:** Fair-Share — Housemate Expense Splitting & Management System  
**Course:** 72ITDS30103 — Software Development Platforms  
**University:** Van Lang University  
**Team:** Võ Việt Tiến, Võ Hoàng Minh, Bùi Duy Anh  
**Coverage:** From project planning through the Final Project assessment (12 November 2026)

## 1. Declaration and overall approach

We used generative AI tools as part of the development workflow for Fair-Share. This included learning unfamiliar technologies, exploring implementation options, obtaining code suggestions, drafting or revising portions of code, investigating errors, discussing test cases, and improving the clarity of documentation. We also used an AI-assisted, sometimes *vibe-coding*, approach: for suitable tasks, we could describe a requirement in natural language and use AI-generated code as an initial implementation rather than writing every line from scratch.

We do not describe AI as merely a spelling checker or claim that all source code was typed manually. At the same time, generating code is not the same as completing a software engineering task. Our responsibility was to decide what the application should do, assess the generated output against requirements, integrate changes into the real codebase, verify behavior, resolve defects, and explain the final solution.

**Our working principle was to treat AI output as a proposal to be checked, not as an authority to be trusted automatically.** The final deliverable is our team's responsibility, regardless of which parts were initially suggested or generated by AI.

This document describes the kinds of AI assistance used throughout the project and the review mechanisms recorded in the repository. Git history and CI results demonstrate engineering activity and checks; they do not, by themselves, measure the exact amount of AI-generated code.

## 2. Project initiation and requirements analysis

During topic selection and early planning, AI helped us think through possible user scenarios, compare feature ideas, clarify unfamiliar concepts, and consider a realistic implementation scope for the course.

The chosen problem was shared-expense management for housemates: creating households, managing members, recording expenses, splitting costs, viewing balances, and settling debts. We organized the requirements into user stories, acceptance criteria, milestones, and assigned work rather than accepting a generic feature list produced by AI.

The project scope and decisions can be checked in [PROJECT_SPEC.md](docs/PROJECT_SPEC.md), [ROADMAP.md](docs/ROADMAP.md), and the GitHub issues/project board. In particular, the course required us to demonstrate the software-development *platform* around the application, not just an attractive interface: a database, Docker/Compose, CI/CD, cloud deployment, and a working AI-enabled feature.

**Human contribution:** selecting and adapting requirements, prioritizing work, assigning ownership, deciding which features were feasible, and updating the plan when deadlines or implementation constraints changed.

## 3. Architecture and technology selection

AI assisted us in understanding architectural alternatives, comparing platform services, interpreting configuration examples, and troubleshooting integration questions. Our documented implementation uses:

- **Frontend:** React, TypeScript, and Vite.
- **Backend:** Python and FastAPI.
- **Data storage:** PostgreSQL; Supabase for the deployed database.
- **Local environment:** Docker and Docker Compose.
- **Continuous integration and delivery:** GitHub Actions and Render.
- **Application AI feature:** Google Gemini API, called from the backend.

We evaluated these choices for compatibility with one another, reproducibility on another machine, the assessment requirements, deployment constraints, and the available free tiers. We also had to handle differences between local development, CI, and production configuration.

Architecture diagrams, API contracts, the database model, deployment decisions, configuration, and trade-offs are documented in [ARCHITECTURE.md](docs/ARCHITECTURE.md). The team was responsible for deciding which suggestions were suitable for Fair-Share and making them work together.

## 4. Coding and implementation: how we used AI-assisted development

Coding was one of the stages where AI support was most directly useful. We used it to accelerate implementation and iteration, especially when working with unfamiliar syntax, libraries, API contracts, components, configuration files, or error messages.

Examples of AI-assisted activities included:

1. Asking for a possible structure for a function, endpoint, React component, or configuration change.
2. Generating a first draft of code from a natural-language requirement (*vibe coding*).
3. Requesting alternative implementations or explanations of why a particular approach might fail.
4. Identifying potential edge cases, suggesting tests, and discussing a failing test or build output.
5. Refactoring drafts for clarity or consistency with the existing project.

The amount and usefulness of generated code varied by task. We do **not** claim that AI only provided tiny snippets, and we do **not** claim that an AI-generated draft became acceptable simply because it compiled.

For every meaningful change, the relevant requirements and existing architecture still had to be considered. The person responsible for the work had to inspect and adapt the result, connect it to the actual application, and verify its behavior. Suggestions that did not fit the data model, security rules, user experience, or API contract were not sufficient just because they looked plausible.

This distinction mattered most for expense splitting and balances, where a small implementation mistake can change users' financial records. Fair-Share represents amounts in integer VND and requires the allocated shares of an expense to add up to exactly its original amount. The backend's behavior, not an AI explanation of it, determines whether that invariant holds.

## 5. Debugging, testing, and independent verification

We did not treat a successful AI response, a clean-looking diff, or a passing syntax check as proof of correctness. The repository documents a workflow with local checks, automated testing, Pull Requests, and code review.

The relevant quality checks include:

- **Backend:** `ruff check .` and `pytest -q`, including tests for expense splitting, balances, data validation, and API behavior.
- **Frontend:** linting, Vitest tests, and production builds.
- **Integration/reproducibility:** a three-service Compose stack and a documented clean-clone rehearsal.
- **Browser behavior:** Playwright checks for important user flows.
- **CI/CD:** GitHub Actions jobs for backend, frontend, images, secrets, deployment, and post-deployment checks as documented in the repository.

A particularly clear example is [PR #113 — the deliberately failing "red gate" demo](https://github.com/NeitLN/Fair-Share/pull/113). This is **an intentional test of our quality gate, not evidence that AI caused the bug**. The branch changes equal splitting so that 100,000 VND divided among three people becomes 33,333 VND each, losing one đồng. The code looks reasonable and passes linting, but backend tests detect the incorrect total and the required CI check blocks the merge. The correct implementation preserves the remainder and the accounting invariant.

This example demonstrates what we consider essential when using AI-generated code: a suggested implementation may look convincing while violating a business rule. Only independent tests, review, and observed behavior can provide confidence.

We also recognize that automated tests are not perfect. A green pipeline is evidence of the checks that actually ran, not a guarantee that the entire application has no defects.

## 6. Git collaboration, authorship, and review

Our repository records a collaborative workflow using issues, dedicated branches, small commits, Pull Requests, reviewer approval, and required checks. These rules are described in [CONTRIBUTING.md](CONTRIBUTING.md).

One particularly relevant rule is that **AI coding assistants are allowed, but the author must be able to explain every line of a Pull Request; code they cannot explain does not count as their contribution**. This is the standard we adopted for AI-assisted work.

Our intended review cycle is:

1. Start from a tracked requirement or issue.
2. Develop or adapt an implementation, with AI assistance where useful.
3. Read the resulting code and check it against the intended behavior.
4. Run relevant lint, tests, builds, and application checks.
5. Open a Pull Request, explain the change, and request another team member's review.
6. Address review findings and merge only when the repository's required checks and approval conditions are satisfied.
7. Confirm the deployed behavior when the change affects the live application.

The Git history and Pull Request discussions provide a record of changes and reviews. We do not equate commit counts or lines changed with effort or learning. Each member remains accountable for the work they present.

## 7. Platform engineering, deployment, and incident handling

AI was useful as a technical reference when working with Docker images, Compose networking, environment variables, database connections, GitHub Actions, Render deployment hooks, and unfamiliar errors. But a suggested configuration still had to be tested in the actual environment.

One documented incident illustrates this approach: in [PR #64](https://github.com/NeitLN/Fair-Share/pull/64), GitHub Actions could report a successful deploy step while the live Render service still served an older commit. A later smoke check exposed the mismatch. The team improved deployment logging so that hook responses and deployment IDs could be inspected, and relied on checking the live commit rather than assuming that a green hook call meant the latest version was running.

The lesson is the same as with application code: neither AI's advice nor a single successful tool status is enough. We need observable evidence that the intended version is actually deployed.

The [README](README.md), [ARCHITECTURE.md](docs/ARCHITECTURE.md), [CLEAN_CLONE.md](docs/CLEAN_CLONE.md), and CI workflow files document how the application can be started, checked, and deployed. We maintained separate local and cloud settings and kept connection strings and API keys out of committed source files.

## 8. Distinguishing AI as a development aid from AI as a product feature

Fair-Share has a product feature called **Quick add**, which uses the Google Gemini API. This is separate from our use of AI tools while developing the project.

A user may enter a sentence such as "Dinner 240k, Minh paid, split three ways." Quick add asks Gemini to help interpret the text and returns a proposed, structured expense draft. It does not directly authorize or save a financial transaction.

The backend and interface provide additional boundaries:

- The Gemini API key is held server-side, not exposed in frontend code.
- Input length, usage limits, and the response format are controlled.
- The returned data is validated, including expense amount and household member names.
- Financial allocation uses application logic rather than trusting the language model to perform the accounting.
- The interface shows the proposed values for the user to inspect and confirm before saving through the normal expense API.
- When Gemini is unavailable, rate-limited, not configured, or times out, the manual expense form remains usable.

These safeguards were part of the product design, not merely an explanation of how our team used AI during development. Their purpose is to make the application's AI feature helpful without giving the model unchecked authority over stored financial data. Technical details appear in [ARCHITECTURE.md §6](docs/ARCHITECTURE.md#6-ai-integration--quick-add).

## 11. Limits, transparency, and responsible use

We recognize several risks in AI-assisted software development: incorrect assumptions, hallucinated APIs, insecure configuration, unhandled edge cases, overcomplicated code, and an inability to explain generated output. These risks are especially relevant when "vibe coding" makes it easy to generate a large change quickly.

To manage them, we aimed to:

- Treat AI suggestions as drafts requiring human judgment and verification.
- Inspect relevant code and understand its logic before taking responsibility for it.
- Use tests and realistic examples to check business invariants and failure paths.
- Seek peer review rather than approving work solely on the basis of AI output.
- Avoid putting secrets, tokens, passwords, or private connection details into public source files or unnecessary prompts.
- Verify deployment against the running service, not just pipeline messages.
- Keep AI-based expense parsing separate from the deterministic accounting and user-confirmation steps.
- Document limitations rather than inventing measurements or claiming untested features.

We have **not** assigned an arbitrary percentage to "AI-written" versus "human-written" code. Repository history does not reliably reveal how a particular line was initially drafted, and the amount of AI support can vary substantially between tasks. A precise percentage without a reproducible method would be misleading.

Our claim is therefore not that AI contributed only a negligible amount. It is that the team remained responsible for the requirements, engineering decisions, code review, validation, integration, debugging, deployment, and explanation of the submitted solution.

## 13. Final statement

We openly acknowledge that AI assisted the Fair-Share project from planning through final delivery, including code generation and vibe-coding-style iteration in parts of the implementation. We do not present AI-generated work as if it were necessarily typed manually, and we do not regard generated output as correct by default.

For this course, our learning and contribution also involve turning requirements into a working system, selecting and connecting platforms, maintaining a usable architecture, testing the behavior that matters, collaborating through reviews, correcting failures, and defending technical decisions. The repository contains evidence of these activities.

**AI helped us work faster and explore solutions; the team remained responsible for deciding what to use, verifying the result, and delivering a working, explainable Final Project.**
